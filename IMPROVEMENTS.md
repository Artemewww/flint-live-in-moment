# 🚀 Улучшения проекта

## 🆕 Сессия 02.10.2026 — надёжность и скорость

### 1. 🛟 Граница ошибок: белый экран → экран восстановления

**Проблема**: `ErrorBoundary` в проекте не было **ни одного**. Любой сбой рендера
давал белый экран. Приложение открывается как Telegram Mini App — там нет
адресной строки и кнопки «назад», поэтому из белого экрана нельзя было выйти:
человек закрывал и заново открывал Mini App, не понимая, что произошло.

**Решение**:
- `src/components/ErrorBoundary.tsx` — ловит сбой рендера, показывает фирменный
  экран с кнопками «Попробовать снова» и «Перезагрузить», текст ошибки — в
  свёрнутом `<details>`, чтобы не пугать обычного пользователя стеком.
- Граница стоит в двух местах: **общая** в `main.tsx` (страховка на весь
  приложение) и **локальная** на каждом ленивом экране. Локальная нужна,
  чтобы падение профиля не вышибало афишу: человек должен терять только тот
  экран, который сломался, а не всё приложение.

### 2. ⚡ Бандл 1054 КБ → 116 КБ (−89%)

**Проблема**: `React.lazy` в проекте не использовался ни разу — всё лежало в
одном куске. `AdminPanel.tsx` (377 КБ исходников) загружался **всем** участникам,
хотя открывается только админом. На мобильном интернете в Mini App это секунды
серого экрана на каждый заход.

**Решение**:
- `src/lazy.ts` — `lazyWithRetry()` вместо обычного `React.lazy`.
- 15 тяжёлых/редких экранов переведены на ленивую загрузку.
- Попутно убрана цепочка статических импортов: `EventFeed` тянул `EventDetailModal`
  (94 КБ), а тот — `SnapModal`. Теперь оба ленивые, иначе ленивая загрузка
  внешне работала бы, но код всё равно ехал в стартовом бандле.
- `vite.config.ts` — `manualChunks`: react / motion / lucide вынесены в
  отдельные чанки **ради кеша**, а не ради порядка в списке. Код приложения
  меняется каждый деплой, вендоры — почти никогда; в общем чанке любая правка
  заставляла всех заново качать 200+ КБ неизменившегося кода.

**Результат** (gzip):

| | Было | Стало |
|---|---|---|
| Стартовый бандл | 287 КБ | **34 КБ** |
| Админка | в стартовом | отдельный чанк 59 КБ, по тапу |

Предупреждения сборки о смешанных статических/динамических импортах исчезли.

### 3. 🔄 Самовосстановление после деплоя

**Проблема**: страница, открытая в момент деплоя, держит в памяти старые хеши
чанков. После деплоя они больше не лежат на CDN, и переход на ленивый экран
даёт 404 → белый экран.

**Решение**: `lazyWithRetry` делает **одну** прозрачную перезагрузку и повторяет
попытку. Флаг в `sessionStorage` не даёт скатиться в бесконечный цикл
«релоад → 404 → релоад», из-за которого страница не открылась бы вообще
никогда. Покрыто 8 юнит-тестами (`src/__tests__/lazy.test.ts`), включая
приватный режим браузера, где `sessionStorage` кидает.

### 4. 🔍 Типы React отсутствовали — `tsc` проверял фронтенд на ноль

**Проблема**: в проекте **не было** `@types/react`, а в `tsconfig` выключены
`strict` и `noImplicitAny`. Из-за этого `tsc --noEmit` исправно рапортовал
«0 ошибок», **не проверяя ни одной строки фронтенда** — импорты React
молча резолвились в `any`. Проверка типов создавала ощущение защищённости,
которой не было: опечатка в пропсах ловилась только в рантайме, то есть
на телефоне участника.

**Решение**: установлены `@types/react` и `@types/react-dom` (19.x), включены
`esModuleInterop`, `forceConsistentCasingInFileNames`, `noFallthroughCasesInSwitch`.
**Результат: 0 ошибок с настоящими типами** — код оказался чистым, просто его
никогда не проверяли. Заодно ушли 4 предупреждения ts-jest.

### 5. 🤖 CI: проверки на каждом пуше

**Проблема**: папка `.github/` была пустой. 97 тестов и `tsc` запускались
только вручную — сломанная сборка спокойно уезжала в прод.

**Решение**: `.github/workflows/ci.yml` — `tsc` → `jest` → `vite build` на
каждом пуше в `main` и на каждом PR. Node зафиксирован на 22: смена LTS может
изменить таргинг esbuild и пересобрать проект без изменения кода.

**Польза**: Устранена путаница для разработчиков, код структурирован.

### 2. 🔐 Централизация проверки Telegram initData

**Проблема**: Функция `verifyInitData()` дублировалась в 3 файлах (`register.ts`, `events.ts`, `profile.ts`). При изменении алгоритма нужно было править все копии.

**Решение**:
- Создан общий модуль `api/_lib/telegram.ts` с утилитами:
  - `verifyInitData(initData, botToken)` — проверка подписи Telegram WebApp
  - `idFromHandle(handle)` — генерация стабильного ID из никнейма
  - `escapeHtml(text)` — экранирование для безопасности
  - `telegramApiCall()` — универсальный вызов Telegram API

- Обновлены файлы:
  - ✅ `api/register.ts`
  - ✅ `api/events.ts`

**Польза**: DRY-принцип, единая точка правды, легче тестировать и поддерживать.

---

### 3. 🛡️ Исправление безопасности админки

**Проблема**: 
- Пароль админки хардкодился в **фронтенде** (`src/admin/AdminLayout.tsx`)
- Любой мог открыть исходники и увидеть пароль
- Атакующий мог перебрать пароли без ограничений

**Решение**:
- Создан серверный эндпоинт `api/admin/login.ts`:
  - Пароль хранится только в `process.env.ADMIN_TOKEN`
  - Сравнение через `crypto.timingSafeEqual()` (защита от timing-атак)
  - Задержка 500–1000ms при неверном пароле (защита от брутфорса)
  - Выдаёт подписанную HMAC-куку на 7 дней
  
- Логика авторизации в `api/events.ts` и других админских файлах проверяет:
  1. HTTP-заголовок `Authorization: Bearer <ADMIN_TOKEN>` (для curl/cron)
  2. Подписанную куку (для браузера)

**Польза**: 
- ✅ Пароль никогда не попадает в публичный бандл
- ✅ Защита от timing-атак и брутфорса
- ✅ Удобный вход через браузер (кука на неделю)

---

### 4. ⏱️ Rate Limiting

**Проблема**: Спам-боты могли отправлять тысячи заявок на регистрацию.

**Решение**:
- Создан модуль `api/_lib/ratelimit.ts`:
  - In-memory хранилище лимитов (для малых нагрузок достаточно)
  - `isRateLimited(key, limit, windowMs)` — проверка превышения
  - `getClientIp(req)` — извлечение IP с учётом Vercel прокси
  - Автоочистка старых записей каждые 5 минут

- Применён в `api/register.ts`:
  - **5 заявок за 15 минут** с одного IP
  - При превышении: HTTP 429 + понятное сообщение

**Польза**: Защита от спама, стабильность сервиса.
